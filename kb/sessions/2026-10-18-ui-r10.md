# R10：邮件提醒确认退避、推送移除清错与空页继续加载

## 概要

按 [协调 brief](../plans/2026-10-18-ui-fixes-coordination.md) 完成 R10 的三项修复。工作基线为 `66403a5`（R10 派发记录，产品代码基线为已签收的 R9 `337b21e`）。邮件 ack 不再因相同 pending 快照自触发忙循环，失败或成功但未移除批次时按批次退避；服务端推送移除账号会清除旧配置错误；聊天连续空页耗尽预算后提供手动继续入口，短会话恢复滚动后也能正确触发首次分页。

所有数据、通知中心与钥匙串均为合成或 recorder；未操作正式 App、飞书、邮箱、凭证或偏好。证据和截图归档在 `tmp/2026-10-18-ui-fixes/r10/`，下文证据路径均相对于该目录。

## 各项结果与根因

### 邮件提醒 ack 忙循环：修好

原调用链是 `ackMail` → `applyNotificationAck` → `apply` → `onNotificationChange` → `request` 设置 dirty → 立即下一轮 GET status、再次 ack。同一快照也执行 apply；成功响应后不检查 pending 是否真的移除，就把同批收据标成 acknowledged。旧代码的 URLProtocol 复现在 0.3 秒发出 534 次 ack，0.6 秒累计 1093 次，任务持续不收敛（`tests-red.log`）。

R7 的“还有未知收据却仍 ack”另有解释：Probe 种下的是 `u1-uncertain-N`，成员也是该假 ID；实际 pending 的目标是 UID 296，标识经 `NotificationRoute.notificationIdentifier` 生成。它们没有指向同一邮件。真实目标没有未知收据，因此实际目标投递/抑制成功后满足整批 handled 条件；不能从这个 fixture 推断“实际未知目标被确认”。匹配真实目标的未知 intent 仍由既有 `interruptedIntentWithoutCenterEntryStaysPendingAcrossRecovery` 等测试验证：没有中心证据时不重弹、不 ack，显式再次提醒才恢复。

修复采用两层控制：

- `applyNotificationAck` 在身份/revision 检查后跳过完全相同的 status 和 pending，不自行制造下一轮。
- 以账号、UIDVALIDITY、batch ID 为 key 记录单调时钟上的下一次 ack 时间；失败或响应仍含该批次时依次等待 1、2、4、8、16、32、60 秒，之后保持 60 秒。只由后续同步、恢复或已有重试入口再次尝试，不创建逐批定时任务。新批次不被旧批次限速，消失的批次和后端世代切换清掉记录。
- 只有 ack 响应已不含该批次才把其收据记为 acknowledged；未移除时保持 handled、未确认和现有失败提示，不重复投递。

真实后端检查结论（源码审阅，未连真实账号）：`mail/api.py` 等待 `MailService.ack` 完成后才返回 status；`MailStore.ack` 在 SQLite 事务内按完整身份更新 acked，pending 查询只返回 acked=0，所以正常匹配的成功 ack 不会留下同一 pending。乱序确认虽然可能暂留数据库行，但该行已 acked，不属于 pending。不存在的 batch ID 是幂等 no-op，其他批次仍 pending；账号或 UIDVALIDITY 过期会抛领域错误；存储错误可失败/回滚，响应丢失也可表现为客户端失败。读删或 reset 抢先移除旧批次后再 ack，不应误清其他批次。这些情况都要求客户端根据权威 pending 收敛，而不能把 HTTP 200 等同于任意 pending 被清空。

复测复用 R7 的原版 `ack_check.py`（只改 run.py 的隔离路径、bundle 和端口）：6 秒内 ack **1 次**、GET `/mail/status` **2 次**，未知收据数仍为 3。见 `ack-check-fixed.json`、`ack-request-counts.json`、`requests.jsonl`。新增 recorder/URLProtocol 测试覆盖成功但 pending 不变、504、连续 30 次触发、指数退避、新批次不受阻、后续成功确认且不重弹；原未知/部分失败/重启/精确中心证据测试全部通过。

### 推送移除后残留错误：修好

`MailState.apply` 在账号变化时已经清凭证、选择和阅读状态，却遗漏 `errorMessage`；用户主动移除路径另外清错，因而只在推送路径残留。将旧错误清理放进账号身份变化分支，覆盖推送移除和身份替换，不清除同账号下新产生的配置错误。

`pushedAccountRemovalClearsOldConfigurationError` 先制造试连错误，再同步应用完整的 `mail.status` 移除事件，确认错误和输入消失。有效 fixture 在旧 `MailState` 上稳定失败（`mail-removal-red.log`），最终通过。

### 会话顶部空页后一直转圈：修好

`loadOlder` 五个空页后仍有游标，但没有让视图区分“暂停等待继续”和“正在加载”。标题仍可见时 task 的 id 不变，不会自动重跑。新增被 Observation 观察的 `needsOlderContinuation`：无更早消息且仍有游标时设置，实际加载开始、换游标或完成后复位；标题显示“加载更早的消息”，点击继续保留的游标，仍无数据也可分预算继续，抵达终点后显示无更早消息。

隔离验收额外复现了同一短会话路径的两个阻塞，均先补失败测试再修：

- 恢复滚动期间原回调忽略历史标题可见性；短内容恢复后几何值不变，首次分页也未触发。恢复期间继续记录真实可见性，task 以“标题可见且恢复完成”为条件。
- 标题重排/再次进入 viewport 时可能自动耗掉下一份空页预算。暂停标记存在时，自动 task 不继续，必须由按钮恢复。真实滚轮和无窗口缩放重进测试均覆盖。

保留普通 VStack、真实 viewport 图片可见性及按可见性分页；没有改回 onAppear。`emptyHistoryBudgetOffersContinuationAndKeepsCursorProgress` 检查五页上限、游标连续、恢复有数据及抵达终点；`shortConversationStartsVisibleHistoryAfterScrollRestoration` 驱动生产 ConversationView，检查首次分页与缩放后仍停在五页。

隔离 App 的 `c-gap` 只有一条当前消息，五个空页的 before_position 为 171、141、111、81、51，按钮点击后从 21 继续，得到最早消息并抵达终点。见 `history-ui-result.json` 与 `history-ui.log`。截图仅截本 App 窗口：`history-empty-budget-{light,dark}.png`、`history-continued-{light,dark}.png`。
