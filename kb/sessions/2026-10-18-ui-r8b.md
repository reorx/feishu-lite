# R8b：展开抄送后地址仍被截断（V1a-01）

## 概要

按 [UI 返修协调 brief](../plans/2026-10-18-ui-fixes-coordination.md) 的 R8b 一节，修 V1a 复验发现的 V1a-01（U1-13 剩下的部分）：富 HTML 邮件（fixture UID 300）展开抄送后，常规和宽窗口里 6 个地址仍被截成一行。起点 `ce0fd7b`，产品代码与 R10 的 `63e323d` 相同。

**结论：修好了。** 原因是邮件头部的 VStack 在摆放时重新分配高度，地址块分到的比量尺寸时少；改成按顺序分配高度的 `TopDownStack` 后，三种窗口尺寸、两种展开方式、深浅色下都完整换行，拉宽、缩窄和真实拖动窗口角的过程中也一样。最小窗口的布局和修改前一致，折叠状态逐像素相同。后端 312、Core 103、App 123（基线 120，新增 3 个），`make build` Debug 成功。

## 根因

邮件头部是 `VStack(spacing:8) { 主题; VStack(spacing:4) { 发件人; 收件人; 抄送 } }`，主题（`lineLimit(4)`）和地址块都能伸缩。SwiftUI 的 VStack 分配高度时，按弹性（最大高度减最小高度）从小到大排序，每个子视图先拿到剩余高度的平均份。

用临时的记录型 Layout 打出各层收到的提议（`tmp/2026-10-18-ui-fixes/r8b/logs/probe-probe-layout.log`，1100 宽的部分摘在 `logs/case-1100.txt`）：

1. 量尺寸：外层把头部提议为 792×667，头部内部的 VStack 得到 641 的高度，地址块先分到 316.5、取 85（抄送 2 行），主题取 40，头部报告 159（内容 133 加上下内边距 26）。
2. 摆放：外层按头部报告的 159 摆放，内部 VStack 拿到的正好是 133，于是重新分配：地址块弹性 15（抄送 1 行到 2 行），主题弹性 20（1 行到 2 行），地址块弹性更小，先分到 (133−8)/2 = 62.5，退到自己的最小高度 70，抄送变回一行，末尾省略；主题拿到 55，取 40。头部总高不变，下面空出 15pt，所以从外面看不出“高度不对”。
3. 最小窗口（800 宽）不出问题：抄送要 3 行，地址块弹性 30，大于主题的 20，主题先分到 70、只取 40，地址块拿到剩下的 100，正好够。

所以是否截断取决于“地址块的弹性是否小于主题的弹性”，和窗口高度、阅读宽度上限无关。这解释了 V1a 的矩阵：最小窗口抄送要 3 行，不截断；常规和宽窗口抄送要 2 行，截断。另外：

- 修改前 1100×720 只展开抄送也截断（`before-v1a-normal-cc-expanded-*`）。V1a 没有截这个组合，不矛盾。
- 实验 A：去掉头部的 760pt 阅读宽度上限，1100 宽仍然截断（`probe/stack-A-no-column-clamp.png`），排除了限宽。

R8 首败第 4 条里“抄送整段文字又被正文挤成一行”的现象，也是同一个原因：问题出在头部内部，`layoutPriority(1)` 只保证外层给头部足够的高度，管不到头部内部的分配。

## 修法

`MailMessageDetail.swift` 新增 `TopDownStack`（一个 `Layout`），替换头部的两层 VStack：

- 从上到下依次分配高度：每一行拿到剩下的全部高度，取自己需要的，余下的留给后面的行。按理想高度摆放时，每一行拿到的都和量尺寸时一样。
- 提议高度为 0 时，每一行仍取最小高度，总高度是各行最小高度之和。分栏按很窄的宽度询问最小高度时，不会像 `fixedSize(vertical:)` 那样被撑高。这一点有测试钉住。
- 竖排、靠左，间距和原来一样：外层 8，地址块 4。

为什么不用别的修法：

- `fixedSize(vertical:)`：brief 和 mac/AGENTS.md 都不允许。窄宽度询问时，抄送文字的理想高度是 2325pt（`probe-probe-layout.log`），会把分栏撑出窗口。
- 在头部内部加 `layoutPriority`：能修好主题和地址块这一层。但收件人、抄送两行都展开、都不超过 8 人时，能不能完整显示要靠“两行最小高度相同”这个隐含条件，不够稳。按顺序分配不依赖 VStack 的排序规则，一个 Layout 管住两层。

展开后的 `VStack(spacing:2) { 地址; 收起 }` 没有换：里面只有地址文字能伸缩，平分不会出问题。超过 8 人滚动、按人数定阈值的设计（R8 的决定）没动。

高度不够时（窗口极矮），`TopDownStack` 会让排在前面的行先拿：主题先保住，抄送最后被压缩。原来 VStack 会让弹性小的先拿。外层仍用 `layoutPriority(1)` 给头部足够的高度，实际窗口里碰不到这种情况。

## 测试

新增 `mac/Tests/FeishuLiteStateTests/MailHeaderLayoutTests.swift`（3 个）。子视图用确定尺寸的视图，数值和截断时实测一致：主题 20–40，地址块 70–85，间距 8，理想高度 133。

- `placingAtItsOwnIdealHeightGivesEveryRowItsIdealHeight`：按自身理想高度摆放时，每行都拿到理想高度，即 40 和 85。
- `minimumHeightStaysTheSumOfMinimums`：宽 10、高 0 的询问返回 98，即各行最小高度之和；高 1000 时返回 133。
- `shortOfHeightTheEarlierRowsKeepTheirs`：摆在 110 的高度里，主题保住 40，地址块退到 70。

先红后绿：先让 `TopDownStack` 暂时等于原来的 VStack，第 1、3 个测试失败，地址块拿到 70，主题拿到 32（`r8b/logs/header-test-red.log`）。再实现 Layout，3 个都通过（`header-test-green.log`）。

`MailNoticeLayoutTests` 里“短头部在 120pt 以内”的断言没改，照样通过，实测仍是 89pt。

## 首败和工具错误

1. `logs/explore-1.log`：第一版探针测试写错了 NSAccessibility 的调用方式（把方法当属性），编译失败。
2. `logs/explore-2.log`：无窗口和不显示的离屏窗口里，NSHostingView 的辅助功能树都只有宿主自己（`AX total 1`），单测里按不到“展开抄送”。改为临时把展开状态的默认值改成 true。
3. 第一次跑记录型 Layout，打印时把 `.infinity` 转成 Int，测试进程以 signal 5 退出。那次的日志被修好后的重跑覆盖了，原始输出只在会话里：`exited with unexpected signal code 5`，崩溃前最后一行是 `PROBE cctext w 0 h 0 -> 0 0`。
4. 第一版拼图脚本没处理透明通道，渲染出来的头部是黑底；改成先叠在白底上再拼。那张黑图被同名的重拼覆盖了。
5. `combo.sh` 第一次在 zsh 的循环里调用，参数没有拆开（`$3: unbound variable`），5 组都没跑；改用 `${=c}` 后重跑。修改前的两组第一次又因为新测试引用了还不存在的 `TopDownStack` 而编译失败；脚本改成跑修改前代码时先把新测试挪开。这几次的日志都被同名重跑覆盖了。
6. 实验 A（去掉阅读宽度上限）没有修好，见“根因”。
7. 整窗像素差不能直接用：侧栏同步时间、悬浮滚动条和 WebKit 正文换行都不同。改为只比详情栏的头部区域，见“验证”。

所有首败都没有记为通过。

## 未验证项

- 没有检查 VoiceOver 朗读顺序、放大字号和全屏。`TopDownStack` 按子视图顺序排列，朗读顺序应该不变，但没有实测。
- 只用了合成数据。真实邮件里很长的姓名和地址、收件人和抄送都接近 8 人时，最小窗口里头部会占多少高度，没有测；按人数定滚动阈值是 R8 的设计，本任务没改。
- 深浅色只在 App 内用 `NSApp.appearance` 切换，没有切换系统外观。
- 没有在 macOS 14 实机上运行。`Layout` 协议从 macOS 13 起可用。
