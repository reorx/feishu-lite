## 一、Herdr skill 的改进建议

### 本次工作暴露的问题与有效做法

最初的问题是派发之后缺少可靠的跟踪和接收结果机制。执行者在新 tab 工作，不会自动拥有协调者的上下文；终端进入 idle/done，也不保证计划已经完成。因此，仅仅开 tab、发 prompt 或拿到命令 exit 0，都不能证明交付成功。

后续有效的流程是：

1. 将任务范围、必读文档、完成标准、报告路径、提交与清理要求写入协调文件，提交后再派发；prompt 只指向具体任务。
2. 开新 Codex tab，保留用户焦点，使用默认模型；有依赖或共享写入范围的任务串行推进。
3. 启动 `wait-settled.sh`，保存 agent、tab/pane、监视任务句柄和报告路径，持续跟踪同一个监视器。
4. 监视器返回后检查真实状态、最终回复、提交、工作区、报告和证据；完成信号只触发审查。
5. 发现缺陷后派修复，再开没写过该修复的新 tab 验收；下一阶段按上一阶段实际结果写任务书。
6. 确认测试进程、通知、钥匙串测试 UUID、隔离偏好与数据已清理，再更新协调状态。

这次行为改善来自把流程固定并持续执行，不能依赖会话记忆在以后自动保留这些习惯。

### 建议如何写进 skill

| 改进点 | 应明确的指示 | 解决的问题 |
| --- | --- | --- |
| 区分代派发与持续协调 | 用户只要求转交时可立即返回；coordinator 默认负责到结果审完 | 避免“开 tab 就算完成” |
| 明确宿主后台机制 | 本次 Codex 环境返回 session ID，需用空输入 `write_stdin` 取结果；Claude Code 可用后台完成通知。先确认当前宿主机制 | 避免把“后台任务完成”误当成“协调者会自动被唤醒” |
| 持久记录监控状态 | agent、tab/pane、任务书、结果路径、等待句柄、状态和审阅基线都写进协调记录 | 压缩或换会话后能续接，不重复派发 |
| 每个 agent 一个监视器 | 等待中断后先确认旧进程与句柄是否仍可用；能续接就续接，确认旧监视器失效后才重建 | 避免两个完成信号引发重复处理 |
| 将停止与成功分开 | idle/done 需检查交付物；blocked、超时、agent 消失、额度暂停分别处理 | 防止半成品或问题对话被当成成功 |
| 明确交付和独立验收 | tab 最后必须回报提交、报告、验证和清理；实机或集成验收有自己的完成标准 | 让结果可审阅，保持协调者角色 |

### 当前 skill 已覆盖什么，还需改什么

本次重新阅读时，技能目录已经有独立的 [herdr-coordinator](/Users/reorx/.agents/skills/herdr-coordinator/SKILL.md)。它明确写了 Codex/Claude 的后台差异、持续协调期间的等待责任、监视句柄持久化、单监视器、恢复流程及交付审查。**以上主要建议已经由当前协调 skill 覆盖，不能继续当作全部待新增内容。** 本会话没有修改这些文件。

仍值得改进的地方：

- 在 [herdr](/Users/reorx/.agents/skills/herdr/SKILL.md) 的长任务段落直接指向 coordinator skill。原文“Run it in the background so that you are notified when it exits”仍缺少宿主前提，应与协调 skill 的具体说明一致。
- 改善监视脚本的结果表达。当前 `wait-settled.sh` 对 idle/done/blocked 都返回 0，必须解析输出文字；可增加结构化状态输出或独立的 blocked 返回码，并同步调用说明。参数 `480` 的单位是**分钟**，不是秒；三次稳定检查的间隔是 45 秒。
- 提供一份可直接复用的状态表模板，包含 agent、tab、监视句柄、报告、提交、状态、审阅基线，减少靠上下文临时保存信息。
- 控制协调开销。平时续接监视句柄，任务开始、交付、阻塞或异常时查看屏幕；进度汇报说新增结论和下一步，不反复发送“仍在等待”。验收任务应限定核心范围，达到 context 门槛后形成准确交接，避免不断扩展矩阵。

## 三、还剩什么，以及建议顺序

### 1. 真实邮箱端到端验收：主要待办

连接凭证已由用户放在 `tmp/feishu-mail.env`，无需重新索要密码；操作 env 必须使用 envops。当前缺少的是**用户指定可以打开并标已读的测试邮件（唯一主题与发件来源），以及新测试邮件的来源/到达安排**。原计划 §7 要求只打开指定目标，因为打开邮件会同步清除其未读。

收到目标后，在新独立 tab 验证：真实文件夹、近期与较早测试邮件、正文与附件信息；SELECT/STORE 的 Seen 持久化、官方端可见与跨端 FLAGS/未读对账；真实新信通知、定位、重连与重启不重复提醒。真实断网、长期 IDLE 和机器睡醒恢复另需适当安排，不能用合成唤醒事件代替。

### 2. 少量交互与系统边界

- 中文 IME 组字、邮箱故障期间可靠的聊天 Return 发送事件，以及 R3 提示按钮的 Tab/Return 焦点；现有自动化未验，不足以确认产品缺陷。
- 稳定账号运行中切换本测试 App 的通知权限、遗留聊天 payload、410/旧账号通知点击，以及系统 add/部分失败等精确路径。已有投递和拒绝权限下启动恢复证据，不能扩大为这些路径也全部通过。
- 历史不同签名钥匙串 ACL、真实拒绝/锁定 UI 与正式发行 App 授权。新 service 隔离已通过，不需要重复跨配置读旧条目或索取用户系统密码。

### 3. 精确安全与时序边界

未知能力稳定加载 UI、旧 HTML navigation/didFinish 及纯文本 layout 迟到回调、已发 STORE 期间账号/UIDVALIDITY 切换、HTTPS/单标签内网实际外开、跨邮件/token 动态访问探测仍按报告保留未验范围。已有自动和实机证据覆盖了许多相邻路径，应做有限补验，不重复全部矩阵。

### 4. 最终签收

真实接入和必要补验完成后，汇总通过/未验/失败，发现缺陷则返修并独立复验，更新原计划、known-issues、next-up 和最终验收报告，再确认整体完成。目前没有从这些未验项新增的确认产品缺陷；不能把“未验”当成“已通过”，也不能自动当成“有缺陷”。

其他文件夹的读取切换、附件下载/预览、发送回复、多账号、邮件串和全文搜索属于明确的下一版范围，**不是本期未完成任务**。发布也未在本次自动执行范围内。
